# Inactivity Screenshot and Daily Report Design

**Date:** 2026-08-10
**Status:** Approved by delegated user decision
**Scope:** `C:\HR\tray_app_maui` and `C:\HR\HRMS-Backend-v1`

## Goal

While an employee is clocked in and monitoring is active, detect continuous keyboard/mouse inactivity. At each five-minute idle boundary, show a Windows notification asking for permission. Capture the combined desktop across all connected monitors only when the employee selects **Allow**. Upload approved screenshots through the Agent Service, store image bytes in private object storage, store tenant-scoped metadata in PostgreSQL, and expose the results in the employee's daily monitoring report.

## Locked Product Decisions

- The first prompt is eligible after 300 continuous seconds without keyboard or mouse input.
- If inactivity continues, a new prompt is eligible at 600, 900, 1200, and later 300-second boundaries.
- Every prompt requires an explicit **Allow** response. A decline, expiry, or no response never captures a screenshot.
- A permitted capture includes the complete Windows virtual desktop across all connected monitors.
- Screenshot bytes are stored in private object storage through `IFileStorageService`; PostgreSQL stores file metadata, capture-attempt metadata, tenant ownership, employee ownership, and report relationships.
- Screenshot bytes are never stored in PostgreSQL, logs, ordinary activity JSON, or the general SQLite collection payload.
- Notification interaction counts as new user input. After Allow or Deny, the next idle cycle starts from that interaction.
- If no response occurs, the pending prompt expires before the next five-minute boundary and the next bucket may issue a fresh prompt.

## Existing-System Findings

- `ActivityCountCollector` already counts keyboard and mouse events without recording keys, characters, coordinates, or clipboard content.
- `IdleDetector` already uses `GetLastInputInfo`, but its current fixed 120-second threshold is not the required five-minute schedule.
- `ScreenshotCollector` currently captures the primary screen every 300 seconds whenever screenshot policy is enabled. It does not wait for inactivity or employee approval and therefore must be replaced by the new workflow.
- `NotificationService` currently writes only to logs; it does not display an actionable Windows notification.
- `Constants.MaxMessageLengthBytes` is 65,536 bytes, so the current base64 screenshot record cannot reliably pass through the line-based Named Pipe protocol.
- `ActivityRecordBuffer` currently places screenshot base64 in ordinary SQLite JSON. The target architecture requires a restricted encrypted evidence spool instead.
- Backend screenshot upload already uses `IFileStorageService`, private object storage, and `MonitoringEvidenceAsset` metadata.
- Backend activity daily summaries and completed work sessions already exist, but daily summaries are generated by a nightly UTC job and do not include inactivity prompt/evidence information.

## Architecture

```text
MonitoringState.Active + valid policy
        |
        v
InactivityMonitoringCoordinator
  polls GetLastInputInfo using a monotonic clock
        |
        | idle crosses 5-minute bucket
        v
WindowsInactivityPromptService
  [Allow] [Skip], correlated attempt id, bounded expiry
        |
        +-- Skip / timeout / activity resumed --> metadata-only attempt
        |
        +-- Allow --> VirtualDesktopScreenshotCapture
                         |
                         v
                   JPEG <= 10 MB
                         |
                         v
              chunked authenticated Named Pipe
                         |
                         v
          Agent Service encrypted evidence spool
                         |
                         v
              ordered retrying HTTP sync
                         |
                         v
        Backend command + IFileStorageService
             |                         |

             |
```

### Responsibility Boundaries

`ONEVO.Agent.TrayApp` owns interactive-session behavior: last-input observation, the actionable notification, virtual-desktop capture, image encoding, and transient chunk transmission.

`ONEVO.Agent.Service` remains the durable authority: it verifies monitoring state and policy, assembles bounded chunks, encrypts the local evidence spool, preserves sync order, owns the Device JWT, uploads to the backend, and deletes local evidence only after acknowledgement.

`ONEVO.Agent.Shared` owns only versioned data contracts, enums, limits, and IPC message types. It contains no Windows, storage, or network implementation.

`HRMS-Backend-v1` authenticates the tray device, resolves tenant and employee identity from the Device JWT, applies effective monitoring policy, stores attempt metadata, sends approved images through the existing private file-storage abstraction, and composes the manager-facing daily report.

## Inactivity State Machine

The coordinator runs only when all of these are true:

- Service state is `MonitoringState.Active`.
- IPC is connected and authenticated.
- `ActivitySignalEnabled` is true.
- `ScreenshotEnabled` is true.
- The Windows session is unlocked and belongs to the active interactive user.

States:

```text
Stopped
  -> Observing
  -> PromptPending(attemptId, bucket)
       -> Capturing       (Allow)
       -> Declined        (Skip)
       -> TimedOut        (notification expiry)
       -> Cancelled       (activity resumes or lifecycle stops)
  -> Observing
```

The coordinator polls every five seconds. It computes `bucket = floor(idleSeconds / 300)`. Bucket zero does nothing. A bucket is prompted at most once within the same continuous idle period. Any new input resets the period and bucket tracking. A semaphore serializes timer ticks, notification callbacks, lifecycle changes, and shutdown so one attempt cannot capture twice.

The notification expires after 270 seconds. This leaves 30 seconds before the next bucket. If the prompt is still pending when the employee becomes active, it is removed and recorded as `activity_resumed`. If **Allow** wins the serialized decision race, capture starts immediately even though clicking the notification updates Windows' last-input time.

Break, clock-out, lock, user switch, policy disablement, or IPC loss cancels the prompt and capture. No capture can start or continue outside the active monitoring gate.

For employee-initiated break and clock-out, the Tray performs a fail-safe pre-stop before sending the lifecycle command: it cancels or dismisses the current prompt, waits for any already-approved capture to finish or fail, submits the final attempt to the Service, and only then sends `StartBreak` or `ClockOut`. Named Pipe writes are serialized, so the Service durably enqueues the evidence attempt before it enqueues work-session completion. If the lifecycle command is rejected and the authoritative state remains Active, the coordinator reconciles and restarts eligible collectors.

## Screenshot Capture

The capture service uses `System.Windows.Forms.SystemInformation.VirtualScreen`, including negative X/Y coordinates, and copies the complete virtual desktop into one bitmap. It returns JPEG bytes with these limits:

- JPEG quality: 75.
- Maximum backend payload: 10 MB.
- If the first encode exceeds 10 MB, downscale proportionally and re-encode until it fits or fail with `capture_too_large`.
- Capture metadata includes monitor count, virtual bounds, encoded byte count, SHA-256 checksum, idle duration, prompt time, decision time, and capture time.

Secure desktop, locked session, zero-sized virtual bounds, capture API failure, or an oversize image produces a metadata-only failed attempt. No raw screenshot bytes or desktop geometry are written to logs.

## Notification Contract

`IInactivityPromptService.PromptAsync` returns one of:

- `Allowed`
- `Declined`
- `TimedOut`
- `ActivityResumed`
- `MonitoringStopped`

The Windows implementation uses a local App SDK notification with **Allow** and **Skip** buttons. The activation argument carries only a random attempt ID and decision token. It contains no employee, tenant, process, or image data. The app registers and unregisters the notification manager during application lifetime.

## IPC and Local Durability

Screenshot bytes are transferred as start/chunk/complete envelopes. Raw chunks are at most 32 KiB so the base64 JSON envelope remains below the existing 65,536-character protocol limit. The transfer contract includes attempt ID, expected byte count, chunk count, content type, SHA-256 checksum, and capture metadata.

The Service rejects transfers when monitoring is not active, screenshot policy is disabled, the declared size exceeds 10 MB, chunks are missing/duplicated/out of order, or the final checksum differs.

The Service protects accepted bytes with DPAPI `LocalMachine` scope and writes them under `%ProgramData%\ONEVO\Agent\EvidenceSpool` with an ACL restricted to the service identity and administrators. SQLite stores only the spool record and metadata. Limits are 256 MB total and 72 hours maximum age. Uploaded files are deleted immediately after backend acknowledgement. Expired or quota-rejected files are deleted and retained only as metadata-only failed attempts.

The general SQLite queue changes from dequeue-and-pre-mark-synced to peek/ack/retry semantics. Records stay pending until the backend acknowledges them. Serialized Tray pre-stop plus ordered Service processing prevents work-session completion from overtaking earlier activity or inactivity-attempt records. A retry reuses the immutable attempt ID as the backend idempotency key.

## Backend Data Model

Add tenant-owned `InactivityCaptureAttempt`:

- `Id` — client-generated immutable attempt ID.
- `TenantId`, `EmployeeId`, `AgentDeviceId`.
- `WorkSessionId` when a session can be resolved.
- `IdleStartedAt`, `PromptedAt`, `DecisionAt`, `CapturedAt`.
- `IdleDurationSeconds`, `MonitorCount`.
- `Outcome` — `captured`, `declined`, `timed_out`, `activity_resumed`, `monitoring_stopped`, or `capture_failed`.
- `FailureCode` — nullable stable code without sensitive text.
- `EvidenceAssetId` — nullable; present only after an approved image is stored.
- `CreatedAt`, `UpdatedAt`.

The primary key gives retry idempotency. Add tenant/employee/date and tenant/device indexes, EF tenant filtering, PostgreSQL RLS, and a foreign key to `MonitoringEvidenceAsset`. `MonitoringEvidenceAsset.TriggerType` is `inactivity_approved` for this workflow. Image bytes remain behind the existing `FileRecordId` and signed-URL flow.

## Backend API

`GET /api/v1/monitoring/tray/policy`

- Uses `TrayDevicePolicy`.
- Resolves effective activity, application, screenshot, and auto-screenshot capabilities for the authenticated employee/device.
- Returns the versioned Agent policy; missing or expired policy fails closed for screenshot capture.

`POST /api/v1/monitoring/tray/inactivity-attempts`

- Uses `TrayDevicePolicy`.
- Accepts multipart form data with attempt metadata and an optional `file`.
- `captured` requires one JPEG file; all other outcomes forbid a file.
- Validates the five-minute minimum, 10 MB size limit, timestamp ordering, monitor count, policy, content type, and authenticated device ownership.
- Upserts by `(tenant_id, id)` and safely returns the existing result for an identical retry.
- Uses `IFileStorageService.UploadAsync` for captured images and stores only `FileRecordId` in evidence metadata.

`GET /api/v1/monitoring/activity/daily-report`

- Uses `TenantPolicy` and `monitoring:read`.
- Returns work-session totals, the activity summary, inactivity outcome counts, and evidence metadata for one employee/date.
- Does not return a permanent file URL. The existing authorized screenshot URL endpoint supplies a short-lived signed URL when the manager opens an image.

## Daily Report Finalization

When a work session is accepted, `SubmitWorkSessionCommandHandler` writes the session and a `monitoring_work_session_completed` outbox message in the same transaction. The outbox handler resolves the legal-entity timezone, aggregates that employee's activity snapshots for the local report date, and upserts `ActivityDailySummary`.

Inactivity attempts and evidence are queried live by employee and local date, so a retried screenshot arriving after clock-out appears without rewriting a report blob. The existing nightly job remains as reconciliation for missed outbox processing and late activity uploads. Re-running finalization is idempotent.

## Error and Retry Behavior

- Deny, timeout, and activity-resumed are normal outcomes, not application errors.
- Backend/network failure leaves the ordered record and encrypted file pending with exponential backoff and jitter.
- `401` attempts one controlled token refresh; persistent authentication failure stops upload and monitoring reconciliation.
- `403` or policy rejection prevents capture/upload and records a safe rejection code.
- `409` with matching immutable attempt data is treated as idempotent success; conflicting data is quarantined.
- Corrupt IPC chunks or spool files are quarantined as metadata-only `capture_failed` attempts without logging image bytes.
- App shutdown, break, clock-out, lock, and IPC loss cancel active prompts and captures.

## Privacy, Security, and Retention

- Keyboard and mouse event content remains forbidden; only counts and idle duration are stored.
- Screenshot capture requires both server policy and per-attempt employee Allow.
- Tenant and employee identity come only from the authenticated Device JWT on the backend.
- Screenshots never appear in logs, exceptions, telemetry, PostgreSQL byte columns, or ordinary activity payloads.
- R2 objects are private and accessed only with short-lived authorized URLs.
- Local evidence is encrypted, ACL-restricted, size-bounded, and deleted after acknowledgement or 72-hour expiry.
- Backend retention uses the monitoring screenshot retention policy and remains legal-hold aware.

## Testing Strategy

Tray unit tests cover exact 300-second bucket behavior, reset after input, repeat prompts, lifecycle cancellation, policy gates, response races, and virtual-screen geometry. Windows manual tests verify actionable notifications and dual-monitor capture.

Service tests cover chunk bounds, transfer checksum validation, state/policy rejection, DPAPI-spool abstraction behavior, SQLite peek/ack/retry semantics, ordering, upload retry, and local deletion only after success.

Backend unit tests cover validators, idempotency, policy enforcement, file-storage calls, aggregation, report composition, and outbox finalization. PostgreSQL integration tests cover Device JWT ownership, RLS isolation, multipart upload, duplicate attempts, report queries, and signed-URL authorization.

## Out of Scope

- Silent screenshots without employee approval.
- Keystroke content, mouse coordinates, clipboard data, audio, video, or browser DOM capture.
- macOS, Linux, Android, iOS, and Tizen support.
- A new manager frontend page; this scope supplies the backend daily-report contract and existing screenshot URL flow.
- Remote push notifications from the backend; the required prompt is a local Windows notification.
