Added four columns to `legal_document_versions`, all `NOT NULL` after backfill:

| Column | Type | Purpose |
|---|---|---|
| `content_json` | `jsonb` | Editor-native document JSON (e.g. TipTap/ProseMirror) |

## Content storage design

- `content_json`/`content_html`/`content_text` are stored verbatim as submitted (after
  validation), `content_hash` is always recomputed server-side by
  `LegalContentHasher.ComputeHash(content_html)` - SHA-256 over the **trimmed** HTML, lowercase
  hex. It is never accepted from the request body; `Create`/`Update`/`Publish` request
  contracts have no `content_hash` field at all (enforced statically by
  `LegalDocumentRichContentArchitectureTests.CreateCommand_NeverAcceptsClientSuppliedContentHash`
  / `UpdateCommand_...`).
- Admin `content_json` request/response fields are typed `System.Text.Json.JsonElement` (not
  `string`) so the wire format matches the spec's examples (`"content_json": { ... }`, a native
  JSON object, not an escaped string). The command layer stores the canonical
  `GetRawText()` string; the detail-response mapper re-parses it with
  `JsonDocument.Parse(...).RootElement.Clone()` for the response.

## Sanitization rules

Implemented as a local, dependency-free, **allowlist-first** validator
(`LegalHtmlValidator` in `src/ONEVO.Application/Features/DevPlatform/Compliance/Helpers/`) -
no HTML sanitizer package existed in the repo, and none was added. Allowlist-first was chosen
over a `<script>`/`onclick`/`javascript:` blacklist because a blacklist only ever covers the
attacks you thought of (`<style>`, `<svg onload>`, an unlisted tag would all slip through a
blacklist; none of them can pass an allowlist that never mentions them).

- Allowed tags: `p, br, strong, b, em, i, u, s, h1, h2, h3, h4, ul, ol, li, blockquote, a,
  table, thead, tbody, tr, th, td`. Any other tag (`script`, `style`, `iframe`, `object`,
  `embed`, `svg`, `div`, ...) is rejected.
- Allowed attributes are per-tag and otherwise empty: `a` -> `href`, `title`; `td`/`th` ->
  `colspan`, `rowspan`. No tag allows `on*` event-handler attributes, `style`, or `class` -
  rejecting them is a consequence of the allowlist, not a separate blacklist rule.
- `href` values must start with `http://`, `https://`, `mailto:`, `/`, or `#`, or otherwise
  contain no `:` before the first `/` (blocks `javascript:`, `data:`, `vbscript:`, etc., while
  still allowing bare relative paths like `docs/page.html`).
- **Every attribute must be quoted and fully consumed** - the scanner walks
  `attributesText` position-by-position (a `\G`-anchored regex re-matched at the exact index
  the previous attribute ended on) and rejects the tag the moment anything - an unquoted
  value, a bare boolean attribute, stray punctuation - doesn't match at that exact position.
  This closed the gap fixed in this pass; see "Production-readiness follow-up" below.
- Validation runs on `content_html` in both `Create` and `Update` handlers before any other
  side effect; a violation returns 400 with a message naming the offending tag/attribute.

## Publish immutability behavior

- **Draft**: fully editable via `Update` (title/content_json/content_html/content_text/
  is_required/block_scope). `document_type`/`version` are immutable from creation onward - the
  `Update` request contract and command have no such fields at all.
- **Published -> Update**: rejected with 409. To change published content, create a new draft
  and publish it.
- **Publish**: `legal_document_versions` carries a non-deferrable partial unique index,
  `UNIQUE(document_type) WHERE status='published'`. `PublishLegalDocumentVersionCommandHandler`
  therefore runs inside `IUnitOfWork.ExecuteInTransactionAsync` with **two** `SaveChangesAsync`
  calls, not one: archive the prior published row for the same `document_type` and flush, then
  mark the new row published and flush. A single batched `SaveChangesAsync` risks EF emitting
  the new row's `published` write before the old row's `archived` write, which the partial
  unique index would reject. This ordering is only actually exercised against real Postgres -
  the in-memory EF provider used in unit tests ignores filtered indexes - which is exactly what
  `LegalDocumentRichContentIntegrationTests.Admin_Can_Create_Publish_And_Publicly_Read_A_Legal_Document_Version`
  asserts (prior row's status flips to `archived`).
- **Archive**: only `status`/`updated_at` change; content fields are never touched (asserted by
  `ArchiveLegalDocumentVersionCommandHandlerTests.Handle_ArchivesPublishedVersion_WithoutMutatingContent`).
  Only `published` rows can be archived (409 otherwise).

## How pending-login users read documents before accepting

Adopted the spec's explicitly-sanctioned Phase 1 simplification: a single anonymous,
published-only public read (`LegalDocumentContentController`) rather than a separate
pending-cookie-scoped endpoint. Both access modes in the spec (authenticated tenant user,
and pending-login user with `onevo_legal_pending` but no session) are served by the same two
routes, since:
- The routes never require any tenant/session context (confirmed safe by inspection - the
  repository methods behind them take no `ITenantContext` dependency and the table has no RLS).
- They only ever return `status = 'published'` rows (`GetPublishedAsync` /
  `GetCurrentRequiredVersionsAsync` both hard-filter on status) - never draft, never archived.
- The response (`PublishedLegalDocumentDto`) contains no `tenant_id`/`user_id`.

`PendingLegalDocumentDto` (returned inline in the login response when
`legal_acceptance_required = true`) now carries two new fields alongside the existing
`content_url`: `content_endpoint` (e.g. `/api/v1/legal/documents/terms/1.1`) and
`content_hash`, populated in `LegalAcceptanceChecker.CheckAsync`. A pending-login user can
therefore `GET` the exact content named in their own pending-acceptance response before
accepting, with no separate authentication step.

## How new versions force re-acceptance

Publishing a new draft archives the prior published row for the same `document_type` inside
the two-phase transaction above. `LegalAcceptanceChecker`/`ILegalDocumentVersionRepository.
GetCurrentRequiredVersionsAsync` (unchanged, pre-existing method) only ever consider
`status = 'published'` rows current - so the moment a new version is published, any user who
only accepted the now-archived version immediately shows up as pending on their next login,
with `content_endpoint`/`content_hash` pointing at the new version.

**Optional acceptance-time verification** (independently droppable, last task in the plan):
`LegalAcceptanceItemInput` gained an additive, default-`null` `ContentHash` parameter. If the
frontend supplies it (in either the in-session `POST /api/v1/legal/acceptances` or the
pre-session `POST /api/v1/legal/acceptances/complete-login` flow), both
`LegalAcceptanceSubmissionService.ValidateAndStageAsync` and
`SubmitLegalAcceptanceCommandHandler.Handle` reject a mismatch with 409. It is never required -
omitting it is unaffected, preserving every existing caller.

added to `LegalHtmlValidatorTests` (`<a href="//evil.example/path">` and

### 1. `LegalHtmlValidator` missed unquoted/malformed attributes

**Flaw**: `AttributePattern` (`([a-zA-Z][a-zA-Z0-9\-]*)\s*=\s*("([^"]*)"|'([^']*)')`) was run
via `Regex.Matches`, which silently skips any substring that doesn't match - so an unquoted
attribute (`onclick=alert(1)`) simply produced zero matches for that attribute instead of an
error, and the tag was accepted as if it had no attributes at all.

**Fix** (`src/ONEVO.Application/Features/DevPlatform/Compliance/Helpers/LegalHtmlValidator.cs`):
replaced the `Matches`-based scan with a position-anchored walk. A `\G`-anchored regex
(`AttributeTokenPattern`) is re-matched starting at the exact index the previous attribute
match ended on; if the next match doesn't start at that exact position (or doesn't match at
all), the tag is rejected as malformed. This means every byte of the attribute text must be
accounted for by a valid, quoted `name="value"` (or `name='value'`) pair - there is no way for
an unquoted or otherwise malformed attribute to be silently skipped.

One side effect had to be handled deliberately: the existing tag regex captures a
space-separated self-closing slash (e.g. `<br />`) inside the same group as the attributes, so
the fix also strips exactly one such trailing `/` before scanning - but only when it sits
outside any quoted value (checked via quote-parity), so a genuinely unterminated quote is still
correctly rejected. Both `<br/>` and `<br />` are covered by new passing tests.

**Examples that now fail** (all confirmed via `LegalHtmlValidatorTests`, which grew from 8
theory cases to 32 total passing tests):
- `<p onclick=alert(1)>Terms</p>`
- `<a href=javascript:alert(1)>Reset</a>`
- `<p class=x>Text</p>`
- `<td colspan=2>Cell</td>`
- `<a href=https://example.com>Link</a>` (unquoted, even though the URL itself is safe)
- `<a href="https://example.com" title=unquoted>x</a>` (one bad attribute rejects the whole tag)
- `<td colspan="2" rowspan=2>x</td>` (mixing one quoted and one unquoted attribute)

Quoted safe content continues to pass unchanged: quoted `href`/`title`/`colspan`/`rowspan`,
`<br>`, `<br/>`, and `<br />`.

### 2. Create/Update commands did not explicitly validate all rich-content fields

Added a new helper class and wired it into both handlers:

- `src/ONEVO.Application/Features/DevPlatform/Compliance/Helpers/LegalContentJsonValidator.cs`
  (new): rejects empty/whitespace `content_json`, invalid JSON, and JSON whose root is not an
  object (rejects a bare `null`, a quoted string, or a JSON array masquerading as the document).
- `src/ONEVO.Application/Features/DevPlatform/Compliance/Helpers/LegalDocumentBlockScopes.cs`
  (new): Phase 1 allowlist - only `dashboard` is accepted, mirroring the existing
  `LegalDocumentTypes` pattern (`terms`/`privacy_notice` only). This is a write-path allowlist
  only; it does not add a DB check constraint, and pre-existing rows/tests that use other
  scopes (e.g. `workpulse_collection`, written directly by `DevSmokeTestTenantSeeder` and by
  `EfLegalDocumentVersionRepositoryTests`, bypassing the command handlers entirely) are
  unaffected, since those document types were already unreachable through
  `CreateLegalDocumentVersionCommand` (`LegalDocumentTypes.Allowed` only permits
  `terms`/`privacy_notice`).
- `content_text` empty/whitespace is rejected with a plain `IsNullOrWhiteSpace` check in both
  handlers (`CreateLegalDocumentVersionCommand.cs`, `UpdateLegalDocumentVersionCommand.cs`).

Validation order (each handler returns on the first failure):
- **Create**: document_type allowlist (400) -> version required (400) -> title required (400)
  -> block_scope allowlist (400) -> content_text non-empty (400) -> content_json valid (400) ->
  `LegalHtmlValidator.Validate(content_html)` (400) -> duplicate version check (409).
- **Update**: not found (404) -> status must be `draft` (409) -> title required (400) ->
  block_scope allowlist (400) -> content_text non-empty (400) -> content_json valid (400) ->
  `LegalHtmlValidator.Validate(content_html)` (400).

`content_hash` remains impossible for a caller to supply: neither
`CreateLegalDocumentVersionCommand`/`UpdateLegalDocumentVersionCommand` nor their API contract
records (`CreateLegalDocumentVersionRequest`, `UpdateLegalDocumentVersionRequest`) declare a
`content_hash`/`ContentHash` property at all - it is always computed by
`LegalContentHasher.ComputeHash(content_html)` inside the handler. This is now enforced by two
*new* architecture tests (`CreateRequestDto_NeverExposesContentHash`,
`UpdateRequestDto_NeverExposesContentHash`) in addition to the two pre-existing ones that check
the command types.

A secondary, related bug was also fixed while wiring this up: `content_json` is bound from the
wire as a `System.Text.Json.JsonElement` and converted with `.GetRawText()` in the controller.
If a caller omits the `content_json` field entirely, the resulting `JsonElement` is `Undefined`,
and `GetRawText()` throws (`InvalidOperationException`, an unhandled 500) rather than failing
cleanly. `AdminLegalDocumentVersionsController.ReadContentJsonText` now maps `Undefined` to an
empty string first, so an omitted field is rejected by the handler's existing
"content_json must not be empty" check (400) instead of crashing the request.

### 3. Migration self-containment

**Decision: not acceptable, made self-contained.** `ONEVO.Infrastructure` already has a project
reference to `ONEVO.Application` (so it compiles either way), but that isn't the concern - the
concern is that migrations are supposed to be permanent, replayable records of exactly what
they did at authoring time. `20260728095359_AddLegalDocumentRichContent.cs` previously called
`LegalDocumentBootstrapContent.TermsHtml` (etc.) and `LegalContentHasher.ComputeHash(...)`
directly from the Application layer. If either of those were later edited - a wording fix, a
rename, a refactor - a from-scratch replay of this migration would silently backfill different
data than it did the first time it ran, with no compiler error and no test failure to catch it
(none of `LegalDocumentBootstrapContentTests`/`LegalContentHasherTests` exercise the migration
itself). That is exactly the kind of drift a migration must never be exposed to.

Fix: the migration now carries its own `private const` copies of every bootstrap literal
(`TermsHtml`/`TermsText`/`TermsJson`, `PrivacyHtml`/`PrivacyText`/`PrivacyJson`,
`GenericFallbackHtml`/`GenericFallbackText`/`GenericFallbackJson`) and its own private
`ComputeContentHash` method (SHA-256 over the trimmed HTML, lowercase hex - byte-identical
logic to `LegalContentHasher.ComputeHash`). The `using ONEVO.Application...` import was removed
entirely. The literals were copied character-for-character from
`LegalDocumentBootstrapContent` and the hash routine is line-for-line the same algorithm as
`LegalContentHasher.ComputeHash` (trim -> UTF-8 bytes -> SHA-256 -> lowercase hex), so the
output is unchanged by construction; this was cross-checked by independently computing
SHA-256(trim(html)) over the three literal HTML strings outside the migration (not by
re-running the migration itself, since it only runs once per database) and getting the expected
64-character lowercase hex digests. No seeded/backfilled content semantics changed - only where
the literals/hash logic physically live.

A new architecture test enforces this going forward:
`LegalDocumentRichContentArchitectureTests.RichContentMigration_IsSelfContained_DoesNotReferenceApplicationHelpers`
reads the migration's source text and asserts it contains no `using ONEVO.Application`,
`LegalDocumentBootstrapContent`, or `LegalContentHasher` reference - mirroring the existing
source-scanning pattern already used by `LegalAcceptanceMigrationIntegrityTests` for the prior
migration. `ApplicationDbContextModelSnapshot.cs` and the `.Designer.cs` file were not touched -
only the hand-written body of `Up()` changed, which doesn't affect either.
