## Schema changes / migrations

Migration `20260813092025_AddChecklistTemplateScopeAndTaskRequiredFlag`:
- `checklist_templates.legal_entity_id uuid NULL` + FK → `legal_entities(id)` RESTRICT + indexes.
- `checklist_templates.position_id uuid NULL` + FK → `positions(id)` RESTRICT + indexes.
- `employee_checklist_tasks.is_required boolean NOT NULL DEFAULT true`.

Applied cleanly to the local dev Postgres database. `Up()` contains only `AddColumn`/`CreateIndex`/`AddForeignKey` — no RLS statements touched (both tables already carried `tenant_isolation` policies from a prior migration, so no RLS regression risk).

**Documented mismatches vs. the vault docs** (full reasoning in the plan's "Documented Mismatches" section):
1. `phase1-table-inventory.md` only documents `checklist_templates.department_id` (nullable/global) — no company or position column exists in any vault doc, yet the userflow doc requires position→department→company matching. Resolved by adding `legal_entity_id`/`position_id` as transitional-nullable columns (same convention as `positions.legal_entity_id`), always set by the new API even though the DB column stays nullable.
2. `employee_checklist_tasks.is_required` is absent from `phase1-table-inventory.md`'s own table definition but present in the Core HR Onboarding/Offboarding module docs and the userflow doc's "Toggle required/optional" action. Added with a compliance-safe `DEFAULT true`.
3. `checklist_templates.tasks_json` due-date shape: the vault doc says "due **rule**", not a concrete date — correct, since a template is reused across many future hires with different start dates. The *pre-existing* code (before this work) would have baked a literal date into `TasksJson` the moment it was ever exercised with a non-empty template (a latent bug, never previously test-covered). Fixed: `ChecklistTemplate.TasksJson` now carries `dueOffsetDays` (relative); `OnboardingDraft.EditedTasksJson` keeps a concrete `dueDate` (HR has already reviewed it against a real date in the wizard).

## Endpoint contracts

| Method | Route | Permission | Description |
|---|---|---|---|
| GET | `/api/v1/people/checklist-templates` | `employees:read` | List (filters: `templateType`, `legalEntityId` [required], `departmentId`, `positionId`, `includeInactive`, `page`, `pageSize`) |
| GET | `/api/v1/people/checklist-templates/{id}` | `employees:read` | Get by id, tasks parsed and returned |
| POST | `/api/v1/people/checklist-templates` | `employees:write` | Create (idempotent via `[Idempotent]`) |
| PUT | `/api/v1/people/checklist-templates/{id}` | `employees:write` | Update (Name/DepartmentId/PositionId/Tasks only — `TemplateType`/`LegalEntityId` are immutable after creation) |
| POST | `/api/v1/people/checklist-templates/{id}/archive` | `employees:write` | Soft-deactivate (`IsActive = false`); no delete endpoint exists |
| GET | `/api/v1/onboarding/checklist-templates/matches` | `employees:read` | Onboarding-only matches for `legalEntityId` [required] / `departmentId` / `positionId`, ordered position → department → company |

Task request/response shape: `ChecklistTemplateTaskRequest(Title, OwnerType, AssignedToId?, AssigneePositionId?, DueOffsetDays, Sequence?, IsRequired)` in; `ChecklistTemplateTaskResponse(Title, OwnerType, AssignedToId?, DueOffsetDays, Sequence?, IsRequired)` out.

## Permission choices

`employees:read` for every GET, `employees:write` for POST/PUT/archive — matching `OnboardingDraftsController`'s existing convention (the closest sibling Core HR feature). Checklist templates are treated as an Employee Management sub-resource, not a distinct module with its own permission pair; no vault doc defines a `checklist-templates:*` permission, so introducing one would have been unrequested scope.

## Task JSON contract

Shared parser (`ChecklistTaskJsonContract`), two modes:
- `ChecklistTaskDueRuleMode.OffsetDays` (`ChecklistTemplate.TasksJson`): `title`, `ownerType`, `assignedToId` (required unless `ownerType == "employee"`, then must be absent), `dueOffsetDays` (int ≥ 0, required), `sequence` (optional), `isRequired` (required, explicit boolean).
- `ChecklistTaskDueRuleMode.AbsoluteDate` (`OnboardingDraft.EditedTasksJson`): same fields except `dueDate` (concrete ISO date, required) instead of `dueOffsetDays`.

Every field is validated by one shared parser; nothing is silently defaulted or dropped — a missing `isRequired`, an unknown `ownerType`, or a negative offset all throw `ArgumentException`.

## Assignee resolution rule

Only `ownerType = "employee"` is deferred: `assignedToId` must be absent in the stored JSON and is resolved to the new hire's own `User.Id` at instantiation time (trivial — that id is already a parameter, not a lookup). Every other owner type (`manager`, `hr`, `it`, `custom_user`) requires a concrete `assignedToId` at template save time, optionally resolved from a chosen position via `IChecklistTemplateAssigneeResolver`:
- Zero active occupants → 422, "provide a concrete assignedToId instead."
- Multiple active occupants → 422, "specify the concrete user/employee... instead" (never auto-picks one).
- `manager`/`hr`/`it` remain informational-only labels in Phase 1 — no manager-chain walk or role-based routing was implemented (would be inventing workflow-engine behavior, out of scope per the task's own instruction).

## Remaining risks

1. `manager`/`hr`/`it` owner types are informational-only in Phase 1 — no automatic assignee routing exists for them. If product later wants "auto-assign to the new hire's manager," that requires a deliberate design decision (position reports-to chain walk), not a silent extension of this contract.
2. `ChecklistTemplate.LegalEntityId`/`PositionId` are schema-nullable (transitional pattern, matching `Position.LegalEntityId`). The API always sets `LegalEntityId`; a direct DB insert bypassing the API could still produce a legal-entity-less template, which `ListOnboardingMatchesAsync`/`GetActiveOnboardingAsync` would then silently treat as never matching any `legalEntityId` filter (since the predicate requires exact equality, `NULL = anything` is never true in SQL) — safe by default, but worth knowing if a seeder or migration ever inserts template rows directly.
3. `UpdateChecklistTemplateCommand` cannot change `TemplateType` or `LegalEntityId` after creation by design (see the handler's doc comment) — flag this as a product-facing constraint if the frontend ever needs "move this template to another company" or "convert an onboarding template to offboarding."
4. Integration tests (RLS cross-tenant isolation, real-Postgres CRUD/matching/instantiation) were never executed in this session — they compile but are unverified against a real database. Re-run `dotnet test tests/ONEVO.Tests.Integration --filter ChecklistTemplatesIntegrationTests` once Docker Desktop is running.
5. Two functions in the same file, `EfChecklistTemplateRepository.GetActiveOnboardingAsync` and `.ListOnboardingMatchesAsync`, duplicate the same position/department/company scope-matching boolean logic inline (no shared predicate helper) — intentional (EF can't easily share a compiled `Expression<Func<...>>` across `Where` clauses with different parameter shapes without extra ceremony), but a future scope-rule change must be applied in both places.
