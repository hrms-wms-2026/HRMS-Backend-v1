# Employee/Position Model Reconciliation Report

## Why users and employees are separate

`users` is the login/security account (credentials, MFA, session, tenant membership).
`employees` is the HR person profile (name, employment dates, legal entity, department). A
user can exist without a fully built-out HR profile (invited-but-not-onboarded), and the two
rows are joined 1:1 via `employees.user_id` (enforced by a unique index) rather than being the
same table, so identity/auth concerns never leak into HR profile concerns or vice versa.

## Why job_title_id and manager_id were removed

Both were placeholders from before the Position model existed:

- `job_title_id` implied a `job_titles` lookup table that Phase 1 explicitly does not build.
  Job title/family/level were already removed from position setup entirely (Phase 1 Position
  Fields Decision) - Core HR has no canonical job-title concept, so a dangling FK-shaped column
  pointing at a table that will never exist was strictly worse than not having the column.
- `manager_id` hard-coded a single flat reporting line directly on the employee row via a
  self-referencing FK. That cannot represent multiple concurrent assignments, position-based
  authority, or org changes over time, and it competes with (rather than complements) the
  Position model's `reports_to_position_id`.

## Proof that Phase 1 reporting belongs to positions/position_assignments, not employees.manager_id

- `positions` already carries `reports_to_position_id` (added by the
  `20260804102821_AddPositionFoundationSchema` migration) - reporting is modeled
  position-to-position, not person-to-person.
- No `position_assignments` or `employee_hierarchy_closure` table exists yet in this codebase
  (both are deferred, listed below). Until they land there is no supported reporting-line
  feature at all, which is exactly why removing `employee.manager_id` regresses nothing: the
  Task 1 audit (full-text search across every non-migration `.cs` file for `JobTitleId`,
  `job_title_id`, `ManagerId`, `manager_id`) found zero references outside
  `Employee.cs`/`EmployeeConfiguration.cs` - no Application feature, controller, or handler ever
  read or wrote either field.

## Migration safety notes

- EF detected both a foreign key (`fk_employees_employees_manager_id`) and its supporting
  index (`ix_employees_manager_id`) on `manager_id` and generated explicit
  `DropForeignKey`/`DropIndex` calls before the two `DropColumn` calls (`job_title_id`,
  `manager_id`) - confirmed by reading the generated migration body.
- `Down()` is fully reversible: it re-adds both columns as nullable `uuid`, recreates the
  index, and recreates the FK with the original `OnDelete(Restrict)` semantics.
- `dotnet ef migrations script` (both idempotent and non-idempotent) was inspected end-to-end:
  the only `DROP COLUMN`/`DROP CONSTRAINT`/`DROP INDEX` statements attributable to this
  migration touch `employees.job_title_id`, `employees.manager_id`,
  `fk_employees_employees_manager_id`, and `ix_employees_manager_id`. No other table or column
  appears in the new migration's block.
- `git status --short src/ONEVO.Infrastructure/Migrations/` after generation showed only the
  two new migration files (untracked) and `ApplicationDbContextModelSnapshot.cs` (modified) -
  no existing migration file was altered.
- The `employees` table itself, and every other column on it (`user_id`, `tenant_id`,
  `legal_entity_id`, `department_id`, `employee_number`, employment type/status/work-mode ids,
  hire/probation/termination dates, avatar), are untouched.

## Remaining deferred work

- `position_assignments` - the actual employee-to-position seat assignment table (who holds
  which position, effective-dated).
- `employee_hierarchy_closure` - a materialized reporting-line closure table derived from
  `positions.reports_to_position_id` + `position_assignments`, for efficient "who reports up to
  whom" queries.
- Employee-to-position assignment APIs (create/change/end an assignment).
- Employee management/profile APIs (the `employees` CRUD surface itself is still pending
  beyond dev-smoke seeding).
