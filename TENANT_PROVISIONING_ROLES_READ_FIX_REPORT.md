# TenantProvisioningE2ETests `roles:read` 403 — Root Cause & Fix Report

**Repo:** `C:\onevoNew\HRMS-Backend-v1`
**Scope:** Fix the deterministic `roles:read` 403 in `TenantProvisioningE2ETests.Full_tenant_provisioning_flow`. No Legal Entity `country_id`/`countries`/logo/asset work touched.

---

## 1. Root Cause

**File:** `src/ONEVO.Infrastructure/Migrations/20260803085232_AddOrgModuleToStarterPlan.cs` (untracked/new, part of today's Department Part 2A batch, never committed or applied outside local runs)

The seeded `starter_51_200` subscription plan (`subscription_plans.id = a1b2c3d4-0001-0001-0001-000000000001`, the exact `SeededPlanId` `TenantProvisioningE2ETests` provisions its tenant on) has its `included_modules_json` column written by three migrations, in this chronological/applied order:

1. `20260509213212_InitialSchema.cs:536` — inserts the row with `included_modules_json = ["core_hr","work_management"]`.
2. `20260510103730_SeedPhaseOnePlanModules.cs:57-62` — updates the same row to the full Phase 1 list: `["auth","configuration","roles","notifications","org","core_hr","leave","calendar","monitoring","workforce","verification","exceptions","analytics","work_management","chat","chat_ai","integrations"]` — **already includes `"org"` and `"roles"`**, two months before today.
3. `20260803085232_AddOrgModuleToStarterPlan.cs` (today, original version) — its own comment claimed the plan was still missing `"org"` (citing only the `InitialSchema` literal value) and overwrote the column with a truncated `["core_hr","work_management","org"]`. This **silently dropped 14 modules** that migration #2 had already added — including `"roles"` — even though `"org"` was never actually missing.

This was independently proven wrong by a second signal: `20260803085232_AddOrgModuleToStarterPlan.Designer.cs:3541` (EF's auto-generated model snapshot at that migration, reflecting `SubscriptionPlanConfiguration.cs`'s `HasData`) already shows the full 18-item list (including `"org"` and `"roles"`). A migration generated by `dotnet ef migrations add` from a diff would never independently hand-write a 3-item `UpdateData` call when the model's `HasData` already has 18 items — confirming this `Up()` body was hand-authored on a stale assumption, not machine-generated from an actual model diff.

**Causal chain to the 403:**

- `roles:read` is defined with `Module = "roles"` (`src/ONEVO.Infrastructure/Persistence/Seeders/PermissionSeeder.cs:167`).
- `CreateTenantCommandHandler.cs:175-178` seeds the tenant's Owner role via `_roleSeeder.SeedOwnerRoleAsync(tenant.Id, plan.GetIncludedModules(), ct)` — `plan.GetIncludedModules()` deserializes `IncludedModulesJson` directly (`src/ONEVO.Domain/Features/SharedPlatform/Subscription/Entities/SubscriptionPlan.cs:25-28`), with no other logic.
- `DefaultRoleSeeder.SeedDefaultRolesAsync` (`src/ONEVO.Infrastructure/Services/DevPlatform/Tenancy/DefaultRoleSeeder.cs:25-41`) grants the Owner role every permission returned by `IModuleEntitlementService.GetEntitledPermissionsAsync(moduleKeys)`, which is `Permissions.Where(p => moduleKeys.Contains(p.Module))` (`src/ONEVO.Infrastructure/Services/SharedPlatform/ModuleEntitlement/ModuleEntitlementService.cs:33-41`).
- With `"roles"` absent from the truncated module list, the Owner role for any tenant provisioned on this plan never received `roles:read`/`roles:manage`.
- `RolesController.List`/`Get` require `roles:read` (`src/ONEVO.Api/Controllers/Tenant/Roles/RolesController.cs:25-26`), so `TenantProvisioningE2ETests`' step 7 (`GET /api/v1/roles` as the freshly-provisioned Owner) returned 403.

**Answering the task's specific checks:**
- `roles:read` exists in the permission catalog and is correctly owned by module `"roles"` — yes, unaffected.
- The module was excluded from the plan used by this exact E2E test (same plan ID) — yes, this was the bug.
- Tenant provisioning does create the Owner role and does assign it to the owner user (both correct) — the role simply lacked this one permission (and 13 others) due to the module-list regression.
- **Did recent Department org-module seeding changes accidentally affect roles/permissions? Yes** — this is precisely that regression, introduced in the same Part 2A batch as the Department feature's `org` module dependency.
- Not a stale test, not RLS, not a cache-invalidation gap, not a provisioning-order issue, not a different plan being used by the test than the fixed seed path — the E2E test and the regressed migration target the exact same plan row.

A unit test (`tests/ONEVO.Tests.Unit/Features/Tenancy/DefaultRoleSeederTests.cs`) written in the same batch as the buggy migration further encoded the regressed 3-item list as "the fixed starter plan module list" and asserted only `org:read`/`org:manage` — never checking `roles:read` — which is why the regression shipped without any red test.

## 2. Fix

**File changed:** `src/ONEVO.Infrastructure/Migrations/20260803085232_AddOrgModuleToStarterPlan.cs`

The migration's `Up()`/`Down()` were rewritten to a no-op: they no longer touch `included_modules_json` at all. `"org"` was never actually missing (migration #2 above already added it), so no seed-data change belongs in this migration. The file (and its migration ID) is kept — not deleted — purely so any environment that already recorded this migration in `__EFMigrationsHistory` sees no ID mismatch; re-running it now does nothing.

This is the smallest correct fix: it removes the accidental regression at its exact source without touching the permission catalog, `RequirePermission` attributes, RLS, or any unrelated seeding path.

### Why this does not weaken authorization or RLS

- No `[RequirePermission]` attribute was touched — `roles:read`/`roles:manage` are still enforced exactly as before on `RolesController`.
- No admin-mode/RLS bypass was added anywhere.
- The fix does not grant any *new* permission — it stops an accidental *loss* of permissions/modules that had already been correctly seeded for two months. The tenant's Owner role ends up with exactly the module-derived permission set it always should have had.
- Nothing in `roles:read` is hardcoded into the test; the E2E test still calls the real `GET /api/v1/roles` endpoint and asserts on the real response.

## 6. Remaining Risk

**This fix does not retroactively repair any already-migrated database.** The original (buggy) `Up()` only ever ran in this session's own Testcontainers-backed test runs (each one fresh, so nothing persists) — this migration was never committed and is confirmed untracked in `git status`. However, if any **persistent local dev database** (e.g. the mkcert-backed `acme.localhost`/`dapi.localhost` environment referenced in prior session notes) already had `dotnet ef database update` run against it after this migration was created, that database's `starter_51_200.included_modules_json` may still hold the truncated 3-item value — rewriting this migration's source file does not change data already written by a prior run of the old code. Anyone using such a persistent database should verify with:

```sql
SELECT included_modules_json FROM subscription_plans WHERE code = 'starter_51_200';
```

and re-seed/re-provision affected tenants if it shows the truncated list. This was not encountered in this session (only fresh Testcontainers databases were used), so it is flagged as a residual risk, not a confirmed live issue.
