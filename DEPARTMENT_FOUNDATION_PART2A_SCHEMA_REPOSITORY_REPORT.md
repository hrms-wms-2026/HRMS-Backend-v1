## 5. Relationship Model

`Department` belongs to both **Tenant** and **LegalEntity** - not either/or. `TenantId` is the RLS/isolation boundary every `ITenantOwnedEntity` table carries; `LegalEntityId` is the Company business boundary docs describe. This is the same dual-FK shape `LegalEntity`, `Position`, and every other Org Structure table already use. Confirmed unanimous across Part 1's doc evidence with no contradiction on this specific point.

## 6. Why Selected-Company Context Is Not Implemented in the Backend

Per this task's explicit product decision: the selected Company/legal entity comes from the **frontend company selector**, and Department APIs in later parts will be scoped by **route parameter** -

```
/api/v1/org/legal-entities/{legalEntityId}/departments
```

- not by a server-side "current selected company" session/header/table. Part 2A's schema and repository reflect this directly: `Department.LegalEntityId` is a normal column (not resolved from any ambient context), and every `IDepartmentRepository` read/query method takes `legalEntityId` as an explicit parameter (mirroring how `ILegalEntityRepository` takes `tenantId` explicitly rather than reading it from a service). No selected-company session/header/table was added, per the task's explicit constraint - there is nothing to defer here; it was never in scope for this backend.

## 7. Migration Summary

**`20260803085109_AddDepartments`** (base table schema):
- Creates `departments`: `id, tenant_id, legal_entity_id, name, code, parent_department_id, is_active, created_at, updated_at`.
- FKs: `legal_entity_id -> legal_entities` (Restrict), `parent_department_id -> departments` (Restrict, self-referencing). No FK to `tenants` - matches the existing `legal_entities` convention, which also has no explicit `tenant_id -> tenants` FK, only a plain index.
- Indexes: `ix_departments_tenant_id`, `ix_departments_tenant_id_legal_entity_id`, unique `ix_departments_tenant_id_legal_entity_id_name` (unfiltered - a deactivated department's name stays reserved within its Company, matching the `legal_entities` name-uniqueness precedent), unique-filtered `ix_departments_tenant_id_legal_entity_id_code` (`WHERE code IS NOT NULL`), `ix_departments_parent_department_id` (tree traversal).
- RLS: enabled via the same `TenantTables` array + `foreach` loop idiom as `AddMissingRlsPolicies.cs` (not one-off inline SQL), so the existing generic `TenantIsolationArchitectureTests.EveryTenantOwnedEntityTable_HasRlsPolicyCoverage` test recognizes `departments` automatically.
- `Down()` is symmetric: drops the RLS policy and disables RLS before dropping the table.

**`20260803085232_AddOrgModuleToStarterPlan`** (data-only fix - see Section 8 for why this exists):
- `Up()`: `UPDATE subscription_plans SET included_modules_json = '["core_hr","work_management","org"]' WHERE code = 'starter_51_200'` (via `migrationBuilder.UpdateData`).
- `Down()`: reverts to the original `["core_hr","work_management"]`.

**`20260803092715_AddDepartmentHeadPositionId`** (corrective schema migration):
- `Up()`: adds nullable `head_position_id` column (`uuid`), index `ix_departments_head_position_id`, and foreign key `fk_departments_positions_head_position_id` to `positions(id)` with `DeleteBehavior.Restrict`.
- `Down()`: drops foreign key, index, and column `head_position_id`.

All migrations were generated with `dotnet ef migrations add` using a placeholder `ConnectionStrings__MigrationConnection` env var.

## 8. Role-Template / Permission Seed Fix Summary

**Correction to Part 1's framing.** Part 1 observed that no `RoleTemplateSeeder.cs` template grants `org:read`/`org:manage` and treated that as the gap. Investigating further for Part 2A showed this framing was wrong: **`RoleTemplate` is a Developer-Platform operator artifact** (`developer-platform/userflow/role-template-management.md` - a platform operator creates/manages global templates that tenant admins can later "apply" to materialize a tenant role). It is not the tenant-owner mechanism, and adding a new named template to it would be inventing a product concept the task didn't ask for.

**The actual tenant-owner mechanism, and where it was actually broken:**
- `DefaultRoleSeeder.SeedDefaultRolesAsync` (`src/ONEVO.Infrastructure/Services/DevPlatform/Tenancy/DefaultRoleSeeder.cs`) creates a per-tenant **"Owner"** role at tenant-creation time and grants it every permission returned by `IModuleEntitlementService.GetEntitledPermissionsAsync(moduleKeys)`, excluding `*` and `ModuleAutoGrants` codes.
- `GetEntitledPermissionsAsync` filters `Permissions` directly by `Permission.Module`. `org:read`/`org:manage` are already correctly seeded with `Module = "org"` (`PermissionSeeder.cs:92-93`), and `org` is already correctly registered as a Phase 1 module (`ModuleCatalogSeeder.cs:60,242-243`). **Nothing was wrong at the permission-definition or module-ownership level.**
- `moduleKeys` comes from `plan.GetIncludedModules()` (`CreateTenantCommandHandler.cs:175-178`), i.e. the tenant's subscribed `SubscriptionPlan.IncludedModulesJson`.
- The only seeded production plan, `starter_51_200` (`InitialSchema.cs:536`), shipped with `included_modules_json = ["core_hr","work_management"]` - **`"org"` was missing.** Every tenant provisioned on this plan therefore never received `org:read`/`org:manage` on its Owner role, even though every other part of the chain was correct.

**The fix:** the `AddOrgModuleToStarterPlan` migration (Section 7) adds `"org"` to that one plan row. No new permission codes were invented (task constraint honored - `org:read`/`org:manage` already existed); no new role/template was invented (only the actual tenant-owner mechanism's input data was corrected).

**Already correct, verified but not changed:**
- The dev/smoke-test seed (`DevSmokeTestTenantSeeder.cs`) already grants both permissions correctly: "Tenant Owner" gets every non-`*` permission (including `org:read`/`org:manage`) via `PermissionCodes = null` -> `ResolveRolePermissionsAsync`'s "grant everything except `*`" branch; "HR Manager" explicitly lists `["org:read","org:manage",...]`. This is proven by the pre-existing `DevSmokeTestTenantSeederTests.SeedAsync_AcmeOwnerBelongsToAcmeWithFullPermissionsExceptWildcard` and `SeedAsync_AcmeHrManagerBelongsToAcmeWithItsRequiredPermissions` tests - unchanged, still passing.
- **Known, deliberately unfixed gap:** `DevSmokeTestTenantSeeder.cs:617,629` hardcodes the dev tenants' `TenantSubscription.SelectedModulesJson = ["integrations","work_management"]` (no `"org"`). This doesn't affect the dev Owner/HR Manager role grants (they bypass `ModuleEntitlementService` entirely, as above), but it does mean `IModuleEntitlementService.IsModuleEnabledAsync(tenantId, "org")` would return `false` for the Acme/Dapi smoke tenants. Nothing in this codebase reads that flag for Org Structure today, so it was left as-is and is called out here rather than fixed silently.

## 10. Head Position Schema Readiness & Application Scoping Policy

head_position_id is schema-ready only. Part 2A adds the nullable database column, EF mapping, index, and FK so the Phase 1 schema is aligned with OneVo-HR. Assigning, changing, validating, or exposing a Department Head Position through API requests is deferred until the real Position APIs/model are ready. Part 2B/2C must not accept headPositionId in create/update requests unless Position validation can prove the position belongs to the same tenant and legal entity/company, is active, and satisfies the approved head-position rules.
